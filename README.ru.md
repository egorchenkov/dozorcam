# Dozorcam

[English](README.md) · **Русский** · [Сайт](https://egorchenkov.github.io/dozorcam/ru/)

Самостоятельно размещаемое видеонаблюдение с интерфейсом в Telegram. Движок пишет
короткий буфер с IP-камер, ищет людей (детектор движения → YOLO) и шлёт снимки и клипы
в forum-группу Telegram: у каждой камеры своя тема, плюс тема «Пульт» с состоянием.
Облака нет: видео живёт в RAM-буфере узла и в вашем чате.

> Проект распространяется «как есть» (см. [CONTRIBUTING](CONTRIBUTING.md#по-русски)):
> это домашний проект одного человека, гарантий поддержки нет.

## Установка в 3 команды

Нужны Linux (arm64 или amd64), Docker с compose и бот от [@BotFather](https://t.me/BotFather).

```bash
git clone https://github.com/egorchenkov/dozorcam.git && cd dozorcam
cp .env.example .env && sed -i 's/^CCTV_BOT_TOKEN=.*/CCTV_BOT_TOKEN=<токен>/' .env
docker compose pull --ignore-pull-failures && docker compose up -d
```

`docker compose pull` скачивает релизный образ `ghcr.io/egorchenkov/dozorcam`; если он
недоступен, `up` соберёт тот же образ локально из `Dockerfile`.

Дальше всё в Telegram (см. «Первый запуск»): `docker compose logs bot | grep SETUP` →
`/start <код>` боту в личку → добавить бота в группу с «Темами» → `/add`.

## Камеры

| Что | Как |
|---|---|
| ONVIF (Profile S) | поиск в локальной /24 и WS-Discovery, потоки и снимок — через ONVIF Media |
| Любая RTSP-камера | `/add rtsp://хост:порт/путь [rtsp://… поток для детектора]` |
| Hikvision (ISAPI) | шаблоны путей RTSP и снимка `/ISAPI/Streaming/channels/101/picture`, где ONVIF молчит; гейт по людям от камеры (ONVIF FieldDetector, `human_gate_mode`) |

Проверено вживую на Hikvision G0/G2/G5 и Tantos. Новую неактивированную Hikvision
активирует сам `/add`: поиск помечает её «🔐», бот просит слово подтверждения, затем пароль
администратора (или генерирует его), а движок активирует камеру (ISAPI-активация V3 или
прежний протокол с challenge), проверяет пароль одним входом, включает ONVIF с отдельным
ONVIF-пользователем, проверяет поток и заводит камеру; «Активировать все» — то же для всех
найденных новых. Пароль показывается владельцу один раз, в личке; копия — в состоянии
движка (`activation-vault.json`, 0600). Камеры других производителей нужно заранее
активировать их средствами; они должны работать через ONVIF/RTSP, но не проверялись.

## Сеть: `network_mode: host` — честно

Оба контейнера работают в сети хоста: движку нужен multicast WS-Discovery и прямой RTSP
к камерам, а мост↔бот без TLS разрешены только по loopback. Цена — нет сетевой изоляции
контейнера: процессы видят все интерфейсы узла и могут ходить куда угодно. Остальное
ужато (non-root uid 10001, корневая ФС только на чтение, `cap_drop: ALL`,
`no-new-privileges`), но если узел смотрит в недоверенные сети — ограничьте исходящий
трафик файрволом хоста. Камеры лучше держать в отдельном VLAN без выхода в интернет.

## Детектор людей: модели, пороги, лицензии весов

| Семейство | Файл по умолчанию | Стартовый порог | Лицензия весов | В образе |
|---|---|---|---|---|
| YOLOX (по умолчанию) | `yolox_tiny.onnx` | 0.30 | Apache-2.0 (Megvii) | да |
| YOLOv5 | `yolov5n.onnx` | 0.35 | AGPL-3.0 (Ultralytics) | нет — скачиваете сами |
| YOLOv8-стиль (YOLOv8, YOLO11) | `yolov8n.onnx` | 0.30 | AGPL-3.0 (Ultralytics) | нет — скачиваете сами |

- В образе только YOLOX-Tiny. Веса под AGPL-3.0 проект не распространяет: если вы
  положили файлы YOLOv5/YOLOv8 в `config/models/`, их лицензия действует для вашей
  установки, а не для кода этого репозитория под Apache-2.0.
- Если всё же нужна YOLOv5/YOLOv8: скачайте или экспортируйте ONNX-файл сами, положите в
  `config/models/` (читаемым для uid 10001) и выберите через `/model` или
  `person_model_family`/`person_model` — по шагам в
  [docs/models.md](docs/models.md#where-to-put-your-own-weights).
- Модель выбирается в `config.toml` (`person_model_family`, `person_model`) или в боте
  (`/model`, смена на ходу с автооткатом). Установки, где уже работала YOLOv5n, остаются
  на ней с тем же порогом 0.35, пока вы не выберете другую.
- **Порог по камере.** После смены модели и по кнопке «🔄 Откалибровать» («🎯 Пороги» на
  пульте) движок набирает ~600 кадров фона на камеру и ставит порог = 99-й перцентиль
  оценки фона сцены + запас 0.10, но не ниже стартового порога модели. Подтверждённые
  проходы (событие из `PERSON_HITS`=2 кадров подряд и/или сигнал человека от самой
  камеры по ONVIF) ограничивают порог сверху, чтобы шумная сцена не теряла уже виденных
  людей. Пока калибровка не закончена — стартовый порог модели. В том же меню любой
  камере можно задать порог вручную: он сильнее автоматического, переживает перезапуск и
  перестаёт действовать при смене модели.
- **Честное ограничение:** автокалибровка находит порог *над шумом*. Полноту (recall) —
  сколько людей пропущено — без размеченных людей не измерить, а людей, которых модель
  не оценивает выше фона, калибровка не видит. Если камера пропускает проходы, задайте
  порог вручную. Подробности и цифры бенча: [docs/models.md](docs/models.md).

## Ограничения

- Время в подписях — Europe/Moscow (часовой пояс пока не настраивается).
- Архива на диске нет: буфер — минуты в RAM, долговременная копия — сам чат Telegram.
- Нужен доступ узла к `api.telegram.org`.
- Автокалибровка порога меряет только шум фона, не полноту (см. выше).
- Языки интерфейса: русский и английский. Другие языки (es, pt-BR, uk, id) планируются;
  сейчас их файлы — пустые каркасы, показывается английский текст.

## Структура

```
cctv/engine/   мост (cctv_bridge), конвейер (cctv_pipeline), RTSP-прокси, провижн,
               ONVIF-гейт движения, детектор людей (YOLO), фильтр неподвижных объектов,
               поиск камер (ONVIF)
cctv/bot/      Telegram-интерфейс (python-telegram-bot), клиент моста, приёмник событий
cctv/i18n/     каркас локализации: locales/<lang>.json
cctv/settings  единый конфиг-каталог /etc/cctv; cctv/cli — точки входа; cctv/notify — личка владельцу
cctv/container супервизор контейнера (роль engine | bot) и его healthcheck
deploy/        systemd-юниты (справочно, установка без контейнера), config.example.toml, secrets.example.toml
scripts/       retention-guard.sh
tests/         engine/, bot/ — из прода; приёмка, связь мост↔бот, конфиг — test_*.py в корне tests/
```

## Разработка

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt && .venv/bin/pip install -e . --no-deps
.venv/bin/python -m pytest -q
```

Точки входа: `cctv-bridge`, `cctv-pipeline`, `cctv-provision`, `cctv-rtsp-proxy`, `cctv-bot`,
`cctv-notify` (или `python -m cctv bridge|pipeline|provision|rtsp-proxy|bot|notify`). Они
сначала читают конфиг-каталог и только потом импортируют модуль: `python -m cctv.engine.…`
в обход них каталог не видит.

## Контейнер

```bash
cp .env.example .env              # токен бота, chat_id, allowed_user_ids
docker buildx build --platform linux/arm64,linux/amd64 -t dozorcam:dev .
docker compose up -d
```

Один образ, роль — команда: `engine` (RTSP-прокси → мост → конвейер под супервизором
`cctv.container`) и `bot`. Оба в сети хоста (ONVIF WS-Discovery, RTSP, loopback мост↔бот),
non-root (uid 10001), корневая ФС только на чтение. Буфер и транзит — tmpfs с лимитом
(`CCTV_BUFFER_TMPFS`, `CCTV_SPOOL_TMPFS`), state — тома `engine-state`/`bot-state`, логи —
stdout с ротацией docker. Конфиг-каталог (`CCTV_CONFIG_PATH`, по умолчанию `./config`)
монтируется только на чтение; его правка перезапускает цепочку внутри контейнера.

Пустой конфиг: без `cameras.json` движок работает с пустым реестром (healthy); без токена
или с отклонённым Telegram токеном бот не запускается и ждёт правки — `docker compose ps`
покажет unhealthy, причина в `docker logs` и `docker inspect` («нет конфига: …»), рестартов нет.

Сборка multi-arch без QEMU: исполняемые шаги идут под платформой сборщика (pip ставит
колёса целевой архитектуры), финальная стадия — только COPY. Нужен containerd image store
(Docker ≥ 29 по умолчанию) или `--output type=oci`. Провижн (`cctv-provision`, root, правит
реестр) в контейнер не входит: реестр в контейнере — файл каталога конфига.

## Первый запуск (мастер)

Достаточно токена бота в `.env`. При первом старте бот пишет в журнал одноразовый код:
`docker logs <бот> | grep SETUP` → `/start <код>` боту в личку (или ссылка `t.me/<бот>?start=<код>`)
делает отправителя владельцем; язык интерфейса — по `language_code` владельца, сменить —
`/lang <код>` (en, ru; другие языки планируются).
Дальше — группа с включёнными «Темами», бот в ней администратор с правами «Управление
темами» и «Удаление сообщений»: бот сам создаёт тему «Пульт» (если чего-то не хватает —
пишет, что включить; повтор — `/setup`). `/add` — поиск камер (ONVIF/RTSP: собственные /24
узла и WS-Discovery, либо `CCTV_DISCOVERY_NETWORKS`), кнопка камеры → «логин пароль»
одним сообщением (удаляется до обращения к мосту) → имя → тема камеры и первый кадр.
Камера вне поиска — `/add rtsp://хост:порт/путь [rtsp://… поток детектора]`.
Модель детектора людей (семейство и файл) — `/model` или «🧠 Модель детектора» на пульте:
смена на ходу, без перезапуска и потери событий, с автооткатом при ошибке загрузки
(подробно — [docs/models.md](docs/models.md)).

Реестр, заведённый из чата, мост пишет сам в `state/cameras.json` (в контейнере — том
движка; `cameras.json` каталога конфига — исходник для пустого state), супервизор видит
смену файла и перезапускает цепочку. `CCTV_CHAT_ID`/`CCTV_ALLOWED_USER_IDS`, если заданы,
сильнее мастера (кода тогда нет). Порог «мало места» в пульте — `CCTV_MIN_FREE_BYTES` движка.

## Конфиг и данные

| Что | По умолчанию | Переменная |
|---|---|---|
| Конфиг (только чтение): `config.toml`, `cameras.json`, `secrets.toml` | `/etc/cctv` | `CCTV_CONFIG_DIR` |
| Состояние (килобайты: пульс детектора, оверлей камер, SQLite бота) | `/var/lib/cctv/state` | `CCTV_STATE_DIR` |
| Буфер сегментов видео (tmpfs) | `/var/lib/cctv/buffer` | `CCTV_BUFFER_DIR` |
| Транзит моста (tmp, media, events) | `/var/lib/cctv` | `CCTV_STORAGE_ROOT` |

Модель детектора людей (в образе YOLOX-Tiny; веса YOLOv5/YOLOv8 — свои), семейства и
пороги: [docs/models.md](docs/models.md).

`config.toml` делится на `[common]`, `[engine]`, `[bot]`; ключ раздела становится
переменной `CCTV_<КЛЮЧ>`, заданная в окружении переменная сильнее файла. Процесс
видит только `[common]` и свой раздел (у моста и бота есть одноимённые переменные
с разным смыслом). Пример — `deploy/config.example.toml`.

Мост↔бот по умолчанию — loopback без TLS (`127.0.0.1:8780` мост, `:8781` приёмник
событий бота); не-loopback адрес без TLS — отказ старта. `CCTV_INTERNAL_TLS=1`
(`internal_tls = true` в `[common]`) включает mTLS в обе стороны для разнесённой
установки.

Уведомления владельцу — личкой от того же бота: сторож бота объявляет «движок не
отвечает / снова отвечает», `cctv-notify` вызывают OnFailure-юниты.
