# Отказоустойчивость

Dozorcam может работать на нескольких машинах сразу, чтобы запасная подхватила движок или
бота. Это отдельный слой поверх супервизора контейнера: сами движок и бот о других узлах
ничего не знают. English: [failover.md](failover.md).

Состояние: **шаг 3 из 5** — режим «наготове», ручное переключение из бота, один конфиг на
всех (активный узел раздаёт его узлам наготове) и несколько движков за одним ботом
([площадки](#площадки-несколько-движков-за-одним-ботом)). Автоматический перехват при падении
узла — следующими шагами.

## Узел и роли

**Узел** — любая машина с Docker, на которой запущена та же пара контейнеров (engine + bot)
из того же образа и с тем же каталогом конфига. Узлы различаются только именем
(`CCTV_NODE` в `.env` узла) и приоритетом в разделе `[failover]` файла `config.toml`.

**Ролей** две: `engine` (камеры, запись, детекция) и `bot` (Telegram). На каждую роль ровно
один активный узел; роли могут быть на разных узлах. Остальные узлы — **наготове** (armed):

- контейнеры запущены, конфиг тот же;
- движок не открывает RTSP и ONVIF к камерам (лимит сессий камер);
- бот не опрашивает Telegram (второй опрос перехватывал бы апдейты и дублировал ответы);
- healthcheck зелёный и пишет `наготове: роль … держит узел …`.

Раз в минуту (`check_sec`) каждый узел проверяет, **пригоден** ли он к своим ролям: голое
TCP-соединение с портом основного потока каждой включённой камеры (без RTSP-запроса, ни
байта) и `getMe` к Bot API. Результат виден в `/nodes`.

Без раздела `[failover]` слоя нет: один узел, обе роли всегда активны.

## Настройка

Всё про узлы лежит в каталоге конфига, а этот каталог активный узел раздаёт остальным (см.
[Один конфиг на всех](#один-конфиг-на-всех)), поэтому все узлы работают на одних и тех же
файлах. Своё у узла только имя.

```toml
# config.toml
[failover]
check_sec = 60                 # период проверки пригодности, 5…3600 с

[[failover.nodes]]
name = "dacha"                 # строчная латиница, цифры, дефис, до 20
priority = 1                   # меньше — главнее; он активен с первого старта
address = "192.0.2.10"         # агенты на :8782 (engine) и :8783 (bot)

[[failover.nodes]]
name = "city"
priority = 2
address = "192.0.2.20"
# engine_agent = "https://192.0.2.20:8782"          # или адреса агентов явно
# bot_agent = "https://192.0.2.20:8783"
# bridge_url = "https://192.0.2.20:8780"            # мост этого узла — для бота на другом
# events_url = "https://192.0.2.20:8781/v1/events"  # приёмник бота этого узла — для движка на другом

# Между машинами агенты говорят по взаимному TLS с CA установки:
# tls_cert = "/etc/cctv/tls/node.crt"
# tls_key = "/etc/cctv/tls/node.key"
# tls_ca = "/etc/cctv/tls/ca.crt"
```

```toml
# secrets.toml (режим 0600)
[failover]
secret = "…"                   # общий ключ подписи запросов агентов, не короче 16 символов
```

```sh
# .env каждого узла
CCTV_NODE=dacha
```

| Ключ | Где | Смысл |
|---|---|---|
| `check_sec` | `[failover]` | период проверки пригодности, по умолчанию 60 с |
| `nodes` | `[failover]` | список узлов, `[[failover.nodes]]` |
| `tls_cert`, `tls_key`, `tls_ca` | `[failover]` | взаимный TLS между агентами; все три или ни одного |
| `name` | узел | имя узла, то же, что `CCTV_NODE` этой машины |
| `priority` | узел | меньше — главнее; по умолчанию — порядок в списке |
| `address` | узел | хост узла; агенты на портах 8782/8783 |
| `engine_agent`, `bot_agent` | узел | адреса агентов явно (два экземпляра на одной машине) |
| `bridge_url`, `events_url` | узел | как роль с другого узла достаёт мост движка / приёмник бота этого узла |
| `secret` | `secrets.toml` `[failover]` | общий ключ подписи |

Что проверяет конфиг (иначе роль не стартует, причина — в журнале и healthcheck): агенты по
голому `http` — только на loopback (два экземпляра на одной машине); между машинами —
`https` с `tls_cert`, `tls_key`, `tls_ca`; неизвестные ключи отвергаются; `CCTV_NODE` должен
называть один из узлов. Каждый запрос между агентами подписан `secret`, ограничен окном
времени и не может быть повторён.

Роли на другой машине нужна и связь движок↔бот по сети: `internal_tls = true` в `[common]`
(см. [справочник: TLS](reference.ru.md#связь-движок--бот-и-tls)) и `bridge_url` / `events_url`
узла.

## Переключение роли из бота

`/nodes` (только владелец) показывает все узлы: где какая роль активна, какие узлы наготове,
пригоден ли каждый и сколько секунд назад его проверяли, и итог последнего переключения.
Кнопки «engine → узел» / «bot → узел» переводят роль; у узла, который не отвечает или не
пригоден, кнопки нет. После подтверждения:

1. текущий узел замораживает роль и подтверждает, что её процессы остановлены;
2. новый узел забирает у него каталог state роли и запускает роль;
3. остальные узлы узнают новое назначение (и сами догоняют раз в `check_sec`).

Двух активных узлов на роль не бывает даже на секунду. Если новый узел не поднял роль, она
возвращается старому. Пока переезжает движок, запись и детекция стоят около минуты; пока
переезжает бот, он молчит несколько секунд и отвечает уже с нового узла — пришлите там
`/nodes` ещё раз.

### Что переезжает с ролью

Только **каталог state роли на диске**: реестр камер и калибровки движка, база бота (темы,
владелец, люди). **Память процессов при каждом переключении теряется** — новый узел
запускает роль с нуля, как после перезапуска: буфер записи, недоведённый диалог `/add`,
события в пути не переносятся. Свои файлы узла остаются на месте: назначение ролей
(`failover.json`), его копия раздаваемого конфига (`failover-config/`, у неё свои ревизии) и
суточная диагностика детектора (`diag/`). Конфиг и настройки из чата на новом узле уже есть —
активный раздал их, пока тот был наготове.

## Один конфиг на всех

Узел, который держит роль, раздаёт свой конфиг узлам наготове — запасной узел всегда готов
подхватить роль с теми же камерами и настройками. Раздаются две вещи, обе по каналу агентов
(между машинами — взаимный TLS с CA установки, каждый запрос подписан `secret`), без участия
движка и бота:

- **каталог конфига** — `config.toml`, `secrets.toml`, `cameras.json`. Каждый агент держит
  копию в своём state (`failover-config/`) с номером ревизии и запускает роль на ней, а не
  на собственном каталоге узла;
- **настройки, сделанные из чата** — файлы state движка, которые бот меняет через мост:
  `cameras.json` (реестр камер), `overrides.json` (камеры на паузе и выведенные),
  `activation-vault.json` (пароли активированных камер), `person_model.json` (выбранная
  модель), `person_threshold.override.json` (ручной порог). Узел наготове пишет их к себе,
  только пока роль у него не запущена.

Правка доезжает до узлов наготове за секунды (держатель проверяет свои файлы раз в 2 с и
сразу рассылает изменение); узел, который был выключен, догоняет при следующей сверке
(`check_sec`). `/nodes` по-прежнему показывает, кто держит каждую роль.

**Где править.** Каталог конфига правят на узле, который держит роль. Правка на узле
наготове не раздаётся (журнал об этом пишет). Новому узлу нужен только раздел `[failover]` в
`config.toml` и `secret` в `secrets.toml` — остальное придёт с активного. После
переключения новый активный узел продолжает работать на полученном конфиге; его собственный
каталог раздаётся, только если до правки совпадал с текущей ревизией — устаревший или
неполный каталог бывшего запасного узла настоящий не перетрёт. Чтобы править там, сначала
возьмите текущие файлы из копии:

```sh
docker compose exec engine cat /var/lib/cctv/state/failover-config/config.toml > config/config.toml
docker compose exec engine cat /var/lib/cctv/state/failover-config/secrets.toml > config/secrets.toml
docker compose exec engine cat /var/lib/cctv/state/failover-config/cameras.json > config/cameras.json
chmod 600 config/secrets.toml
```

Присланную ревизию, на которой узел не запустится (сломан TOML, неизвестный раздел, этого
узла нет в `[failover]`), узел не принимает: остаётся на прежней и на связи, чтобы получить
исправление. Файлы сертификатов (`tls_*`) и `secret` канал сам себе поменять не может — они
нужны ему для работы, поэтому их меняют на каждом узле.

**Окружение узла.** С разделом `[failover]` раздаваемый конфиг сильнее собственного
окружения узла (`.env`): устаревшее значение в `.env` запасного узла не перебьёт то, что
раздал активный. Своё значение сохраняют только узловые ключи:

- имя узла и пути внутри контейнера: `CCTV_NODE`, `CCTV_CONFIG_DIR`, `CCTV_STATE_DIR`, `CCTV_BUFFER_DIR`, `CCTV_STORAGE_ROOT`, `CCTV_RUNTIME_DIR`, `CCTV_SUPERVISOR_STATUS`, `CCTV_CAMERA_CONFIG`, `CCTV_PROXY_CAMERA_CONFIG`, `CCTV_RUNTIME_CAMERA_CONFIG`, `CCTV_REGISTRY_FILE`, `CCTV_REGISTRY_SEED`, `CCTV_PROVISION_SOCKET`, `CCTV_PROVISION_BACKUPS`, `CCTV_PROVISION_UNITS`, `CCTV_RETENTION_GUARD`, `CCTV_MODEL_DIRS`, `CCTV_NOTIFY_STATE`
- адреса и порты этой машины: `CCTV_BIND`, `CCTV_PORT`, `CCTV_PUBLIC_URL`, `CCTV_EVENTS_HOST`, `CCTV_EVENTS_PORT`, `CCTV_EVENTS_URL`, `CCTV_BRIDGE_URL`, `CCTV_RTSP_PROXY_PORT`, `CCTV_NODES_URL`, `CCTV_NODES_TOKEN`
- свои сертификаты связи движок↔бот: `CCTV_BRIDGE_CA`, `CCTV_BRIDGE_CLIENT_CERT`, `CCTV_BRIDGE_CLIENT_KEY`, `CCTV_CLIENT_CA`, `CCTV_SERVER_CERT`, `CCTV_SERVER_KEY`, `CCTV_EVENTS_CA`, `CCTV_EVENTS_CERT`, `CCTV_EVENTS_CLIENT_CA`, `CCTV_EVENTS_KEY`, `CCTV_BRIDGE_USER`, `CCTV_BRIDGE_GROUP`
- её сеть и сервер Bot API: `CCTV_DISCOVERY_NETWORKS`, `CCTV_TELEGRAM_API`
- её память, диск и процессор: `CCTV_BUFFER_MAX_BYTES`, `CCTV_BUFFER_SEGMENTS`, `CCTV_MAX_TOTAL_BYTES`, `CCTV_STORAGE_BUDGET_BYTES`, `CCTV_MIN_FREE_BYTES`, `CCTV_CV_THREADS`, `CCTV_DETECT_NICE`, `CCTV_PERSON_INFER_SLOTS`

Всё остальное — настройки установки: им место в `config.toml` или `secrets.toml`, а не в
`.env`. Новая настройка, которая не поехала бы с раздаваемым конфигом, валит
`tests/test_failover_config.py`.

## Площадки: несколько движков за одним ботом

**Площадка** — набор камер со своим движком; обычно это место со своей сетью (дача, город).
Один бот обслуживает несколько площадок сразу: каждый движок шлёт события в приёмник бота, а
бот кладёт их в ту же группу и те же темы — тема принадлежит камере (`camera_id`), а не
движку. Камера, переехавшая с одного движка на другой, остаётся в своей теме. Движки ничего не
знают ни друг о друге, ни о площадках: у каждого свой реестр камер и обычная связь движок ↔ бот.

Площадки — список в разделе `[bot]` файла `config.toml`:

```toml
[bot]
sites = ["dacha", "city=https://192.0.2.20:8780"]
```

- `имя=адрес` — площадка и адрес моста её движка; просто `имя` — мост самого бота
  (`bridge_url`; при `[failover]` он следует за ролью движка, то есть это площадка, чей движок
  переезжает между узлами). Имя — строчная латиница, цифры и дефис, до 20 знаков; две площадки
  с одним именем или одним мостом не запускаются.
- Нет `sites` — площадка одна и неявная, ровно как раньше: одномоторная установка не меняется,
  список из одной площадки — тоже.
- Между машинами связи нужен `internal_tls = true` в `[common]`: у каждого моста сертификат
  от CA установки, бот ходит ко всем со своим клиентским сертификатом
  ([справочник: TLS](reference.ru.md#связь-движок--бот-и-tls)). Без TLS допустимы только адреса
  loopback (два движка на одной машине для проверки).
- `sites` — настройка установки, а не узла: при `[failover]` она едет в раздаваемом
  `config.toml`, и бот находит те же площадки, на каком бы узле он ни работал.

Что бот делает с несколькими площадками:

- **реестр камер** — камеры всех площадок; камера без своего тега локации показана на карте в
  разделе своей площадки. Id камеры, который есть на двух площадках, принадлежит первой по
  списку (журнал об этом пишет) — давайте камерам разные id;
- **кнопки камеры** (кадр, клип, пауза, имя, настройка, порог) уходят мосту её площадки, медиа
  берётся только с того моста, откуда пришло событие;
- **`/add`** спрашивает, на какой площадке камера: поиск в сети, активация и проверка пароля идут
  через движок этой площадки — только он достаёт до своих камер. `/add <площадка>` и
  `/add <площадка> <адрес>` — без вопроса;
- **модель детектора** одна на установку: `/model` показывает каталог первой площадки и меняет
  модель на всех; пороги всех площадок — одним списком;
- **молчащая площадка** не останавливает остальные: её камеры остаются с состоянием «нет
  кадров» (ничего не снимается), другие площадки продолжают публиковать события. Только когда
  молчат все, бот сообщает, что мост не отвечает.

При `[failover]` один движок — площадка без адреса в `sites` — это роль движка слоя: у него
есть копия наготове на другом узле, и он переезжает через `/nodes`. Движки остальных площадок
работают на своих машинах вне слоя, со своим каталогом конфига. Чтобы их события находили бота,
на каком бы узле он ни работал, перечислите в их `events_url` приёмник бота каждого такого
узла — движок отдаёт событие первому, кто его принял (бот наготове порт не слушает):

```toml
[engine]
events_url = ["https://192.0.2.10:8781/v1/events", "https://192.0.2.20:8781/v1/events"]
```

## Два экземпляра на одной машине

Для проверки без второй машины: две копии compose-проекта с разными
`COMPOSE_PROJECT_NAME`, портами (`CCTV_BRIDGE_PORT`, `CCTV_EVENTS_PORT`,
`CCTV_RTSP_PROXY_PORT`) и `CCTV_NODE`, общий каталог конфига и агенты на loopback явно:

```toml
[[failover.nodes]]
name = "dacha"
engine_agent = "http://127.0.0.1:8782"
bot_agent = "http://127.0.0.1:8783"
bridge_url = "http://127.0.0.1:8780"
events_url = "http://127.0.0.1:8781/v1/events"

[[failover.nodes]]
name = "city"
engine_agent = "http://127.0.0.1:8792"
bot_agent = "http://127.0.0.1:8793"
bridge_url = "http://127.0.0.1:8790"
events_url = "http://127.0.0.1:8791/v1/events"
```

## Чем проверено

- `tests/test_failover_armed.py` — движок наготове не запускает процессов и шлёт камере
  0 байт (только TCP-connect), не трогает порт снимков/ONVIF и поток детекции; бот наготове
  вызывает только `getMe`, никогда `getUpdates`.
- `tests/test_failover_switch.py` — два настоящих процесса супервизора с настоящим ботом
  против мока Bot API: `/nodes` и кнопки переводят бота туда и обратно; Telegram опрашивает
  один узел за раз, на каждое действие — ровно один ответ, проверка пригодности видна в
  панели. Движок переезжает туда и обратно через клиент панели бота; его процессы никогда
  не живут на двух узлах сразу; каталог state переезжает, память процессов — нет.
- `tests/test_failover_boundary.py` — движок, бот и общий код не импортируют слой;
  супервизор берёт у слоя только «включись/замри»; настройки слоя — только из общего
  каталога конфига (из окружения узла — одно `CCTV_NODE`), и каждый ключ описан здесь.
- `tests/test_sites.py` — два настоящих моста движков с разными камерами и один бот, всё по
  взаимному TLS: установка начинается с одного движка, бот заводит темы; потом камеры
  разъезжаются по двум площадкам со своими движками, бот перезапускается на той же базе с
  `sites`, новых тем не заводит, а события, которые оба движка шлют одновременно, ложатся в
  прежние темы своих камер; пауза камеры доходит только до движка её площадки; `/add`
  спрашивает площадку; молчащая площадка сохраняет свои камеры и не останавливает соседнюю;
  движок с двумя приёмниками в `events_url` доставляет запущенному, когда первый закрыт.
  Совместимость: без `sites` — прежний клиент одного моста, список из одной площадки ведёт себя
  так же; неверный список — отказ старта.
- `tests/test_failover_config.py` — два узла по взаимному TLS, у каждого свой каталог
  конфига (у запасного — только `[failover]` и устаревшие значения): первая ревизия, правка
  каталога на активном и настройки из чата доезжают до узла наготове за секунды без ручных
  действий; клиенту без сертификата установки агент не отвечает; после переезда движка новый
  активный узел работает на полученном конфиге и свой устаревший каталог не раздаёт, а правка
  поверх текущей ревизии уходит обратно. Предохранители: новый файл каталога конфига, новый
  файл настроек в state роли, настройка мимо `CCTV_*`, настройка, которая не последовала бы
  раздаваемому конфигу, или узловой ключ без описания валят тест; присланная ревизия, на
  которой узел не запустится, не принимается. Так же едет список площадок: добавленный на
  активном узле, он доезжает до узла наготове и сильнее устаревшего `CCTV_SITES` в его `.env`.
