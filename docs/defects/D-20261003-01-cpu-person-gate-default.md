# D-20261003-01: движок 0.1.0 по умолчанию гоняет YOLO на каждом кадре и молча теряет сегменты

Статус: пп. 1–2 исправлены в 0.1.1 (06.10.2026), п. 3 открыт · найден 03.10.2026 на теневом прогоне 0.1.0 рядом с исходным конвейером
(4 камеры: 2 × 720p 25 к/с, 2 × 720p 10 к/с, 1 × 1080p 25 к/с — последняя по main-потоку).

## Симптом

Движок 0.1.0 с настройками по умолчанию на тех же четырёх камерах занимал весь лимит
контейнера 1.5 CPU (~1.5 ядра), исходный конвейер — 0.55–0.6 ядра. Детектор отставал на
~600–670 с и держался ровно там, а 4 из 11 настоящих проходов за 50 мин не нашёл.

## Причины (замер, 1 поток OpenCV, ARM Neoverse-N1, process_time)

| Фактор | Цена | Вклад |
|---|---|---|
| YOLO на кадр: YOLOv5n 640 | 277–282 мс CPU | — |
| YOLO на кадр: YOLOX-Tiny 416 (умолчание 0.1.0) | 301–316 мс CPU | +10 % к цене кадра |
| Декод всех кадров сегмента (grab + read каждого stride-го) | 0.02–0.03 ядра на камеру 720p, 0.09 на 1080p 25 к/с | одинаково в обеих системах |
| Frame-diff гейт (to_gray + motion_score) | 1.4–3.4 мс на кадр | пренебрежимо |
| Выборка кадров | 2 к/с на камеру (`CCTV_RECORDED_PERSON_FPS`) | одинаково |

**Главная причина — `CCTV_PERSON_GATE_MODE` по умолчанию `shadow`.** В shadow гейт только
считает решение, а YOLO идёт на каждом выбранном кадре: 4 камеры × 2 к/с = 8 прогонов/с ×
~0.31 с ≈ **2.5 ядра** спроса. В enforce на тех же камерах гейт открыт для 0–16 % кадров
(сцена без движения — 0–1 %), YOLO ≈ 0.8 прогона/с ≈ **0.23 ядра**. Это ×10 по самой дорогой
части; модель (YOLOX против YOLOv5n) даёт лишь +10 %.

**Вторая — тихая потеря кадров при нехватке CPU.** `RecordedMainStream._open_next` берёт
следующий сегмент по имени после последнего разобранного; если буфер (`CCTV_BUFFER_SEGMENTS`
=120 × 5 с ≈ 10 мин) уже удалил отстающие сегменты, курсор молча перепрыгивает. Отсюда
lag, «прилипший» к ~10 мин, и фактическая выборка ~0.96 к/с вместо 2 — половина видео не
просматривалась, а в журнале ни строки об этом.

## Что сделать в приложении

1. Умолчание `person_gate_mode = "enforce"` (shadow оставить режимом диагностики) — исходный
   конвейер работает в enforce с 04.09.2026; в README указать цену shadow.
2. Журналировать пропуск сегментов: `detector_skipped_segments camera=… count=… lag=…`, и
   показывать «детектор не успевает» в статусе бота — сейчас перегруз незаметен.
3. В бенч моделей (`bench/`) добавить цену кадра в ядро-секундах рядом с recall: YOLOX-Tiny
   дороже YOLOv5n на ~10 % при 1 потоке.

Проверка обхода на 0.1.0 (без правки кода): в `config.toml` `[engine]`
`person_gate_mode = "enforce"` (+ при желании `person_model_family = "yolov5"`).

## Исправлено в 0.1.1

1. `PERSON_GATE_MODE` по умолчанию `enforce`; `shadow` описан в `deploy/config.example.toml`
   как диагностический (~10× CPU).
2. `RecordedMainStream` пишет `detector_skipped_segments camera=… count=… lag=… total=…`, когда
   буфер удалил неразобранные сегменты; 10 минут после пропуска (`CCTV_DETECTOR_BEHIND_HOLD_SEC`)
   пульс детектора — `behind`, бот показывает «детектор не успевает» в панели и сообщает о смене
   состояния. Тесты: `tests/engine/test_recorded_main_stream.py`, `tests/bot/test_cctv_*`.
